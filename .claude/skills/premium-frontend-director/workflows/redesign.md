# Redesign an existing frontend

## Inputs

Use the requested outcomes, current site or codebase, assets, user-approved constraints, and any migration requirements.

## Procedure

1. Inventory routes, responsive states, content, design tokens, forms, analytics, CMS fields, APIs, authentication, and core journeys. Capture screenshots or existing visual baselines when available.
2. Separate the incumbent visual direction from functional and content contracts. Preserve the latter unless the user explicitly expands scope.
3. Identify the largest usability and communication problems with evidence. Do not replace familiar elements just to create difference.
4. Create a new direction that fits the audience and authentic content. Define how navigation, mobile, forms, and existing integrations map into the new design.
5. Implement in coherent route/component groups. Keep URLs, CMS contracts, analytics, APIs, and permissions stable unless change is approved.
6. Compare representative before/after routes and verify primary journeys, responsive states, accessibility basics, and runtime output. Fix observed defects in a bounded pass.

Load [design-direction](../references/design-direction.md), [frontend-engineering](../references/frontend-engineering.md), and [content authenticity](../references/content-and-brand-authenticity.md); add other references as needed.

## Deliver

Summarize the new direction, preserved contracts, routes/components changed, checks run, regressions found or not assessed, and remaining rollout needs.

## Acceptance

- The new design has a consistent rationale and is not a superficial reskin.
- Existing user journeys and functional contracts remain intact or approved changes are documented.
- Real content and source assets remain accurate and appropriately licensed.
- Mobile and desktop behavior are verified where tools permit.
